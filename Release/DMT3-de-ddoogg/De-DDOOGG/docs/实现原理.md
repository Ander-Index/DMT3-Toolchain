# De-DDOOGG 实现原理 — DMT3 双狗免狗技术文档

> 面向维护者的实现说明。分析全过程见 `DMT3_Toolkits\docs\` 系列文档（00–20）。

---

## 0. 总览

游戏受两只加密狗保护：

| 狗 | 型号 | 保护机制 | 免狗方案 |
|---|---|---|---|
| 狗① | Senselock EL（VID_0471&PID_485D） | 设备枚举（SetupDi/QueryDosDeviceW）+ 0x22 挑战-应答（TEA，会话密钥绑定当次 48B 熵） | itoken2v2 虚拟驱动（枚举面）+ multiDLL 罐头重放（应答面） |
| 狗② | Rockey6 SMART PLUS | 65 字节 HID 帧会话（WriteFile/ReadFile） | vrockey6 虚拟驱动（枚举面）+ multiDLL 用户态 RW 拦截（应答面） |

三个组件缺一不可：**multiDLL.dll（用户态代理）+ itoken2v2（内核驱动）+ vrockey6（内核驱动）**。

### 0.1 双版本代理（红外 / 触控）

游戏的 multiDLL.dll 存在两个**各有用途**的变体：红外屏原版（24KB）与民间触控屏适配版
（214KB，启动时弹 "Multi Emulator" 窗口）。两者导出完全相同（OpenNexioMulti /
CloseNexioMulti / WaitNexioMulti），故代理做成同一二进制、仅转发目标文件名不同的
两个 flavor：

- `proxy_ir.dll` → 转发 `multiDLL_orig.dll`
- `proxy_touch.dll` → 转发 `multiDLL_touch.dll`

部署 = 把所选代理复制为游戏目录的 `multiDLL.dll`，两个转发目标常驻游戏目录即可。
构建开关在 `build_rw_replay.py` 顶部 `BACKING = 'orig' | 'touch'`。

## 1. multiDLL.dll — 用户态代理（核心）

游戏经 import 加载 `multiDLL.dll`（导出 OpenNexioMulti/CloseNexioMulti/WaitNexioMulti）。
我们把原版改名 `multiDLL_orig.dll`，放入自构建的代理 DLL（`scripts\build_rw_replay.py` 生成，
纯汇编经 keystone 组装 + 自研 pebuild 打 PE 包）。DllMain 内联 hook（5 字节 E9）：

- `kernel32!DeviceIoControl`（狗① 通道）
- `kernel32!ReadFile / WriteFile`（狗② 通道）
- `advapi32!SystemFunction036`（RNG 观察，FIX_RNG 可强制置零，默认关）

### 1.1 狗①：t7 罐头重放引擎

- 录制：透传模式下把每次 ioctl 落成 8224B 记录（`dumps\ioctl_zerorng.log`，299 键 / 368KB 应答）。
- 键 = `(ioctl, insz, outsz, inbuf[0:64])`，掩码合并运行期堆指针/令牌字节；同一键多次出现
  **按序**存储（cursor 推进 + 回绕），1:1 复现录制序列。
- **会话密钥自洽性**：会话密钥 = f(0x390008 返回的 48B 熵)，与 RtlGenRandom 无关。
  0x39（熵）与 0x22（挑战）必须来自同一录制 run —— REPLAY_39 固定 + REPLAY_22 罐头即满足。
- **0x47 铁律**：0x47 是 cfgmgr32/SetupDi 设备枚举 ioctl，**必须透传**（罐头会喂给系统过期数据）。
- 0x470800「open」是异步 ioctl：罐头必须写 `OVERLAPPED.InternalHigh` 并 `SetEvent`，否则游戏死等。
- 0501（insz=17）响应里的 4B 指针值本身被游戏校验，必须原样回放录制值。
- 罐头应答加 10ms 延迟（REPLAY_DELAY_MS），模拟真狗 USB 往返，防止游戏校验循环空转。

### 1.2 狗②：RW 状态机拦截

- 65B、buf[7:9]=="R6" 的 WriteFile 识别为狗②命令：cmd1=ATR、cmd2=挑战（8/16B 密钥查表）、
  cmd3=会话 blob（3×65B 分段，按会话序播出）。应答来自录制转录（rw_song.log 等），编译进 DLL。
- 未知挑战回放任一结构合法的 0e 帧（游戏接受），全零帧会被拒。
- 空闲 65B ReadFile 必须**透传真实阻塞**（立即返回会让游戏空转）。

### 1.3 关键 bug 修复记录（2026-08-28，曾致「REPLAY_22 崩溃」假象）

`restore_one`（hook trampoline）第二个 `VirtualProtect` 在 `xchg esi,edi` 之后误用 `esi`
（此时指向自身 .data 备份区），把 g_origX 所在 .data 页（与 g_rec/g_rec2 日志缓冲区同页）
置成 RX → 下一次 dump_buf 写日志即 AV → 游戏在任何记录落盘前死亡（0 条记录 + VMP fast-fail）。
修复：第二个 VirtualProtect 目标改用 `edi`（=目标函数）。**archive 里的旧脚本带病，勿恢复。**

## 2. itoken2v2 — 虚拟狗①枚举驱动（drivers\itoken2）

root 枚举的内核驱动（WDM），提供游戏两步枚举所需的全部表象：

- 注册设备接口 GUID `{171638f7}`，reference 串含 `Vid_0471&Pid_485e`
- 注册 `\DosDevices\ITOKEN2`（游戏 QueryDosDeviceW 匹配 "ITOKEN2" → `\\.\ITOKEN2`）
- 0x47 枚举类 ioctl 由它被动透传应答（真实应答方），0x22/0x39 在到达它之前已被 multiDLL 罐头
- 安装：`pnputil /add-driver itoken2.inf /install` + `devcon install itoken2.inf root\vid_0471&pid_485d`
  （hwid 故意选 root\vid_0471&pid_485d，让设备路径自带 VID/PID 串）

## 3. vrockey6 — 虚拟狗② HID 驱动（drivers\vrockey6）

MsHidKmdf 架构（hidclass 为 function driver，vrockey6.sys 为 lower filter），root 枚举出
HID 设备供游戏打开；实际 65B 帧应答由 multiDLL 在用户态拦截完成，驱动只需存在并可打开。

## 4. 签名与测试模式

两个驱动均为自签名测试证书 **DMT3 De-DDOOGG**（sha256，有效期至 2099-12-31）签名。目标机器需：

1. `bcdedit /set testsigning on`（重启一次）
2. 导入 `DMT3-De-DDOOGG.cer` 到 `本地计算机\受信任的根证书颁发机构` + `受信任的发布者`

（install.ps1 自动完成。）

## 5. 数据流一图

```
Client.exe
   │ DeviceIoControl(0x47 枚举) ──► multiDLL 透传 ──► itoken2v2（虚拟设备，应答枚举）
   │ DeviceIoControl(0x39 熵)   ──► multiDLL 固定回放（zerorng run）
   │ DeviceIoControl(0x22 挑战) ──► multiDLL t7 罐头（同 run，会话密钥自洽）
   │ WriteFile/ReadFile(65B R6) ──► multiDLL 狗②转录状态机
   └ 其他 I/O ──► 全部透传
```

## 6. 已知边界

- multiDLL 日志路径硬编码 `D:\DMT3\*.log`（其他游戏目录仅无日志，不影响功能）。
- 罐头数据绑死当前游戏版本；游戏大版本更新若改动 EL 调用序列需重录。
- 真狗官方驱动（slusb/slvbus/slvrd）与本方案互不影响，可共存。
